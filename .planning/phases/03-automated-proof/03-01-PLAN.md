## Decisions this plan makes (planner's discretion, flagged for review)

CONTEXT.md locks the mechanisms. These are the choices it left open, surfaced
because 03-02, 03-03 and every SC-5 control bind to them.

1. **The tree is materialised by `git archive --format=tar HEAD` read through Go's
   stdlib `archive/tar`** — not by piping to an external archiver, and not by
   `git worktree add`. CONTEXT.md D-07's 2026-09-03 correction requires this choice
   to be made deliberately rather than ported from `02-03-PLAN.md`'s bash
   verification step, because unlike that one-shot the Go form runs on every gate,
   in CI, on Windows and Linux. Four reasons, in order of weight:
   (a) **No build-host dependency.** The bash form shells out to an external
   archiver; the Go form needs only the standard library, so `go.mod` and `go.sum`
   stay byte-unchanged, matching the discipline 02-02 held for the harness itself.
   (b) **It leaves nothing behind in the repository.** `git worktree add` registers
   an entry under `.git/worktrees/`, and D-07 records that `DefaultTimeout` exists
   because these children can hang and that a `defer` does not survive a timeout
   kill. A killed test leaves a stale worktree registration that only
   `git worktree prune` clears; it leaves a plain temp directory that
   `os.RemoveAll` clears idempotently.
   (c) **The extraction loop is where the traversal and entry-kind guards live.**
   A shell-out extraction has nowhere to put them. Measured before planning: all
   230 tracked files are mode `100644`, with zero symlinks and zero executable
   bits, so the loop handles exactly regular files and directories and treats
   anything else as a hard failure — which is what makes a future symlink surface
   as a loud failure rather than as a quietly different tree.
   (d) `git archive HEAD` is content-deterministic, so the copy compiles against
   the shared content-addressed `GOCACHE` and builds warm.
   Rated `reversible` — the materialiser is one function behind one signature; a
   later switch to `git worktree` changes it and nothing else.
2. **A condition's proof and its SC-5 control are two subtests of ONE top-level test
   function**, with the intact-tree `RunResult` captured in the parent's scope.
   D-16 requires the control to reuse the proof's captured result rather than
   re-running it; the alternatives were a package-level variable (which makes the
   control depend on cross-test execution order and breaks under `-shuffle=on`) or a
   memoised accessor (which would have `gate.Run` calling `t.Fatalf` on a
   `*testing.T` belonging to a different test). Subtests give guaranteed ordering
   inside one `*testing.T` lineage, and they leave the guard genuinely trippable:
   running only the control subtest leaves the captured result at its zero value and
   the guard fires. D-13's "three controls, one per condition" is satisfied — three
   control subtests, one per condition, never one shared control. Rated `reversible`.
3. **`lineContainsBoth(combined, a, b string) bool`** is the same-line predicate:
   split on the newline byte, trim one trailing carriage return, report whether any
   single line contains both substrings. It is NOT built on `extraLines`, which
   solves a multiset-diff problem, not a same-line-conjunction one. It gets its own
   control driving it against synthetic inputs — including the case D-18 exists to
   rule out, the two substrings on two adjacent lines — reusing Phase 1's
   `preambleInvariant` shape: a pure decision function exercised against inputs that
   make it say no. Rated `reversible`.
4. **Each control materialises its own copy; no tree is shared across tests.**
   CONTEXT.md's discretion note allows sharing "where the tree contents allow"; they
   do not, cheaply — sharing needs a package-lifetime memo, which reintroduces
   exactly the cross-test coupling decision 2 removed. Extracting 230 small files is
   negligible beside a nested gate run, and D-16's measured saving was the intact
   gate run, which is still not repeated. Rated `reversible`.
5. **Test names carry the requirement ID without its hyphen** (`TestPROOF01_...`,
   since Go identifiers cannot contain one), so each test's doc comment carries the
   hyphenated form — which is also what the GOV-01 close sweep's ID derivation
   matches on. Rated `reversible`.

## Assumption-delta decision

The `assumption-delta` detector fired `pluralization` on this phase's scope. The
signal it matched is prose about GOV-01, but the phase does contain a real instance,
so it is decided here rather than dismissed.

- **Noun now primary:** *the package that owns make-invoking tests*. Phase 2 had
  exactly one (`internal/platform/gate`); this phase introduces a second
  (`internal/platform/gateproof`).
- **Decision: `add-alongside`, deliberately.** D-03 rejected promoting a single
  general "make-invoking tests" package — relocating `makefile_test.go` would edit
  frozen Phase 2 deliverables named by file in `02-02-SUMMARY.md`, manufacturing a
  GOV-01 instance rather than finding one. The asymmetry is not accidental: the two
  packages have different jobs. `gate` owns the harness and may reach its own
  unexported helpers; `gateproof` owns the proofs and may not, and that inability is
  the enforcement mechanism, not a side effect.
- **Accepted debt:** two packages contain tests that shell out to `make`, and a
  reader can reasonably ask which is the home for a new one. The rule: a test ABOUT
  the harness goes in `gate`; a test that USES the harness to prove gate behavior
  goes in `gateproof`.
- **What would force a promote:** a third such package, or `gateproof` needing a
  helper that only `gate`'s internals can provide. The second would mean the
  exported surface is wrong, which is precisely the signal D-03 built the boundary
  to send.
- **Invariant test:** already covered rather than added — the boundary is enforced
  by the compiler on every build, which is stronger than a test.
