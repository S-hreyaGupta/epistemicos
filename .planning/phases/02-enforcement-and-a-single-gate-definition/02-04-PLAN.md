## The two halves of GOV-01, and which plan owns which

| Half | What | Where it lives |
|---|---|---|
| **Start check — mechanism** | the standalone comparison, runnable by a human at any time, reused unchanged by Phase 3 | **this plan** |
| **Start check — enforcement** | a `<precondition>` on the phase's first plan that halts on disagreement | `02-01` Task 1 |
| **Close sweep** | the full derived-artifact sweep, after every plan and after UAT and security sign-off | `02-05`, its own final plan |

D-13 requires both halves of the start check because neither survives alone: a
target nobody is forced to run is an intention, and a precondition does not travel
to the next phase. This phase's precondition spells its comparison out longhand
because the target is this plan's own output; from Phase 3 onward the precondition
invokes the target instead. That bootstrap is recorded rather than hidden.

## What this plan does NOT do

- It does not run the close sweep. That is 02-05, deliberately in its own final
  plan, after UAT and security sign-off — the checkpoints that produced all four
  instances GOV-01 tabulates.
- It does not make parity a Go test. D-13 rejected that on its own cost: it would
  make `make gate` fail on docs-only drift, changing what the gate means in the
  one milestone whose entire purpose is that the gate means exactly one thing.
- It does not extend D-15's tagging convention beyond PROJECT.md. CONTEXT.md
  records that as a deferred idea — defining and enforcing a documentation
  convention is not this phase's work.
- It does not correct PROJECT.md's stale claims. Four of its six `— Pending`
  Key Decisions outcomes describe Phase 2 work and go false when this phase lands.
  Tagging is what makes the close sweep **see** them; correcting them is the close
  sweep's job in 02-05, and doing it here would be the sweep running before the
  events it exists to catch.
</objective>

  <action>
Create `scripts/` and `scripts/planning-parity.sh`, a POSIX-shell script run as
`bash scripts/planning-parity.sh <phase-number>`. It performs three checks and
exits non-zero if any fails, reporting all failures rather than stopping at the
first — a check that hides the second disagreement behind the first would need
running twice to be trusted.

**Check 1 — the argument.** With no phase number, exit non-zero naming the missing
argument. Do not default. A default would report agreement about a phase nobody
asked about, which is the shape of failure GOV-01 exists to remove.

**Check 2 — requirement-set parity (D-13).** Extract set A from `.planning/ROADMAP.md`:
locate the `### Phase <N>:` heading, read forward to the next `### ` heading, and
take the requirement IDs from the `**Requirements**:` line within it. Extract set B
from `.planning/REQUIREMENTS.md`'s `## Traceability` table: every row whose Phase
cell names phase `<N>`. Compare the two sets in both directions and report each
difference under its own heading, so a reader sees which document is missing what.

Two parsing constraints, both grounded in the current files rather than assumed:

- The phase match must tolerate a **trailing parenthetical** — GOV-01's Phase cell
  reads `Phase 2 (closure gate)` and must count as Phase 2.
- The phase match must not match a **longer number** — `Phase 2` must not match
  `Phase 21` or `Phase 2.1`, both of which the roadmap's decimal-phase convention
  makes possible. Anchor the match so the digits are followed by something that is
  not a digit or a decimal point.

Extract requirement IDs with a pattern of uppercase letters, a hyphen and digits,
so the parser does not need a hard-coded list of prefixes and a new prefix is
handled the day it is introduced.

**Check 3 — PROJECT.md requirement-ID validity (D-15).** Extract every requirement
ID appearing in `.planning/PROJECT.md`, and assert each one appears in
REQUIREMENTS.md's traceability table. Report any that do not, naming them. This is
what stops a typo becoming coverage: a wrong ID would otherwise produce a sweep row
for a requirement that does not exist, and a phantom row reads exactly like a
checked one. Note in a comment that this check is deliberately one-directional — it
does not require every requirement to be tagged in PROJECT.md, because most are
not and should not be.

**Output discipline.** Print sorted, deduplicated lists so two runs of the same
